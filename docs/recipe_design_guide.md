# レシピ・原稿の設計ガイド（スパゲッティ化を防ぐために）

pptmdmerge は変数置換・条件つきの処理・番号マーカーを持つ「文書のコンパイラ」になりつつある。プログラムと同じで、切り替えを場当たりに足していくと、どの条件で何が出るのか誰にも分からない状態になる。このガイドは、そうならないための**書き方の約束**と、**ツールに入れない機能**をまとめたもの。

検査で守れるものは `pptmdmerge validate` が警告する（[validation.md](spec/validation.md#validate)）。ここに書くのは、検査では判断できない設計上の約束。

## 1. 書き方の約束

### 1.1 切り替えに使う変数は `params:` で宣言する

`--var` で切り替える変数は、レシピ冒頭のコメントではなく `params:` に書く。取りうる値・既定値・説明を書いておけば、打ち間違いは読み込み時にエラーになり、`validate --list-params` がそのまま「このレシピのつまみ一覧」になる。

```yaml
params:
  SHOW_ANSWERS:
    type: bool
    default: false
    description: 解答例を問題の直後に出す（レシプロマーカー向け）
```

- **置換用（`vars:`）と切り替え用（`params:`）を混ぜない。** `COVER_TITLE` のように文字を埋める変数は `vars:`、出し分けに使う変数は `params:`。同じ名前を両方に書くとエラーになる。
- 冒頭コメントの「起動パラメータ」の説明は `description:` に移す。

### 1.2 変数は「出力先」ではなく「意図」で名付ける

`TARGET=RECIPRO` で切り替えている内容が実際には「解答例をすぐ出すかどうか」なら、`SHOW_ANSWERS` のように意図で名付けた方が、各 `when:` を読んだだけで何のための条件か分かる（同じコメントを何十回も書かずに済む）。

出力先ごとに複数の意図をまとめて切り替えたいときは、出力先ごとのビルドスクリプトやコマンド行で `--var` を並べる。1 つの変数に複数の意味を持たせない。

```bash
# レシプロマーカー向け
pptmdmerge ppt_to_pdf book.yaml --var SHOW_ANSWERS --var MULTISTEP
```

### 1.3 切り替えの軸は 3 本まで

変数が 3 本なら組み合わせは 2×2×2=8 通り。それ以上は全部をビルドして確かめることが事実上できない。4 本目が欲しくなったら、レシピを用途ごとに分ける（共通部分は `!include`）ことを先に検討する。

### 1.4 分岐はレシピで、文中の微差だけ MD で

| 切り替えたいもの | 書く場所 |
| ---- | ---- |
| ページ・スライド・ファイル単位の出し分け | レシピの `when:` / `group:` |
| 文中の一言二言、注記 1 行の違い | MD / ノートの `{{#if}}` |

ページ単位の分岐を MD の `{{#if}}` に書くと、レシピを読んでも全体の構成が分からなくなる。`{{#if}}` が 1 ファイルに何十行も続くなら、ファイルを分けて `when:` で選ぶ。

### 1.5 同じ条件は 1 か所にまとめる

同じ `when:` を 3 回以上書くなら `- group:` にまとめる（`validate` が info で提案する）。区切り（`insertvfill` / `insertpagebreak`）も一緒に group に入れてよい。

```yaml
  - group:
      - insertmd: q1_answer_md.md
      - insertvfill
      - insertmd: q2_answer_md.md
    when:
      var: SHOW_ANSWERS
```

### 1.6 入れ子は浅く

- `{{#if}}` は 2 段まで（3 段以上は `validate` が警告）。
- `group` は入れ子にしない（2 段以上は警告）。条件ごとに group を並べる。

### 1.7 否定より肯定

`!NAME` や `NAME!=VALUE` は、変数が**未定義でも真**になる。打ち間違えても「出る」ので気付きにくい。肯定形（`NAME`、`NAME=VALUE`）で書けるならそちらを使う。`params:` で宣言していれば打ち間違いは読み込み時にエラーになるが、肯定形の方が読みやすいことは変わらない。

### 1.8 番号マーカーは 1 行に 1 つの意図

- `{{nolabel}}` / `{{noref}}` / `{{nonum}}` は `{{#id:}}` と同じ行に書かないと効かない。
- `{{nonum}}`（採番しない）と `{{nolabel}}`（採番はしてラベル置換だけしない）は意図が違う。併用しない。

### 1.9 レシピを変えたら validate

レシピ・原稿を直したら `pptmdmerge validate recipe.yaml` を流す。自動化するなら `--strict` で警告も失敗にする。

切り替えの効き方は `pptmdmerge explain recipe.yaml --matrix NAME` で確かめる（値ごとに採用／除外が変わる項目だけが並ぶ）。この出力をファイルに保存して git で管理すれば、レシピを編集したときに意図しない項目が入った／消えたことが diff で分かる。

## 2. ツールに入れない機能

言語機能を足すほど、レシピは読めなくなる。以下は**意図的に入れない**。必要に見えたら、まず「レシピを分ける」「`--var` を並べる」で解決できないかを考える。

| 入れない機能 | 理由 / 代わりの手段 |
| ---- | ---- |
| 条件式の and / or / 括弧、else-if | `when.var` のリスト（OR）と、`when` のキー同士・group の入れ子（AND）で足りる。複雑な式は読めない |
| 変数から変数を作る（派生変数・式・変数の中の変数展開） | 値の出どころが追えなくなる。必要な値は `--var` で直接渡す |
| ループ・繰り返し | 項目は並べて書く。同じ構成の繰り返しはレシピの生成スクリプト側で |
| マクロ・ユーザー定義の操作 | procedure の操作は固定の語彙にとどめる |
| 条件つき `!include` | `!include` は読み込みの最初に展開される。条件は `when:` / `{{#if}}` で |
| 型の追加（数値・範囲など） | `params:` は `bool` / 列挙（`values`）/ `string` の 3 つ |

この表に入れたい機能が出てきたら、仕様を変える前に、どの実例のどの困りごとを解決するのかを書き出して判断する。
