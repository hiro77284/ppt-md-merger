# 設計メモ: pptx アニメーションの段階キャプチャ

> **ステータス:** **案 C を採用・実装済み**（2026-10-23）。`pptimgexport` の `export-image-step:` として動作確認済み（§6.5）。§1 は**現在の実装の事実**、§2〜4 は検討メモ、§5 が試作の実測結果、§6 が採用した記法と実装方針。

## 1. 現状と制約

`pptimgexport` は**アニメーションに非対応**。実装は次の 2 段だけで、アニメーション関連の処理はコードベースに存在しない。

1. python-pptx で pptx を開き、ノートの `{{BLOCK:IMAGE}}` 指示とシェイプ座標を読む
2. pymupdf で「スライド番号と同じ PDF ページ」を指定 DPI でラスタライズし、矩形で切り出す（[pptimgexport/__init__.py:61](../src/md_merge/pptimgexport/__init__.py), [同:309](../src/md_merge/pptimgexport/__init__.py)）

**PDF 経由では原理的に対応できない。** PowerPoint の PDF 書き出しは 1 スライド = 1 ページで、すべてのオブジェクトが配置された状態を 1 枚描くだけ。開始アニメーションで後から出る要素も終了アニメーションで消える要素も同じページに写り、タイミング情報は PDF に残らない。クリック送りで 3 段階に出る図は、PDF 上では「3 段階すべてが重なった最終状態」の 1 ページしかない。切り出し側をどう工夫しても中間状態は取り出せない。

python-pptx は `p:timing`（アニメーションのタイムライン XML）を読むことはできるが、評価・描画する機能はない。pymupdf は出来上がった PDF しか見えない。つまり現在の構成はどちらの層にも「段階を描画する」能力を持たない。

## 2. 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| **A. 原稿側で段階をスライドに分ける** | アニメを使わず、段階ごとにスライドを複製して未出現シェイプを削除/非表示にしておく | コード変更ゼロ。既存パイプラインがそのまま動く。手作業と保守が重い。**当面の前提** |
| **B. 段階スライドを自動生成する前処理** | `p:timing` を解析し、ステップごとにスライドを複製して該当シェイプを隠した pptx を生成 → 以降は今の PDF→切り出しがそのまま使える | 既存アーキテクチャを壊さない自動化案。無人実行可・PDF 品質・再現性あり。実装は重い |
| **C. COM でスライドショーを駆動しウィンドウキャプチャ** | `View.Next()` でステップを進め、各段階を画像として取得 | 実装は比較的軽くアニメの見た目に忠実。対話セッション必須・環境依存（§4） |
| D. 動画書き出し（`CreateVideo`）してフレーム抽出 | MP4 からタイムスタンプでフレームを拾う | 同期が曖昧で画質も落ちる。実用性が低い |

## 3. 案 B のメモ（無人実行・品質を優先する場合）

- `p:timing` のクリックステップを解析し、ステップ k ごとにスライドを複製して「k 以降に出現する」シェイプを `p:cNvPr@hidden="1"` で隠した pptx を生成する
- 難所: 段落単位のビルド（テキストを行ごとに出す）、グループ、SmartArt / グラフのビルド、終了アニメーション。シェイプ粒度に丸めて警告する妥協も選択肢
- **生成した段階スライドを非表示にしないこと**。非表示スライドは PDF に出力されずページ番号がズレ、`pptimgexport` のスライド→ページ対応が崩れる（既知の落とし穴）

## 4. 案 C のメモ（COM 駆動＋ウィンドウキャプチャ）

### 駆動はキー送信ではなく COM

- `Presentation.SlideShowSettings.Run()` → `SlideShowWindow` が返る
- `SlideShowWindow.View.Next()` が**クリック 1 回ぶん = アニメーション 1 ステップ**進める（スライド 1 枚ぶんではない）
- `View.GetClickCount()` / `GetClickIndex()` でスライドの総ステップ数と現在位置が取れる。`View.GotoClick(n)` で任意ステップへ跳べる
- `SlideShowSettings.AdvanceMode` を手動送りにして自動時間送りを止める
- SendKeys 方式はフォーカスを奪われると壊れるが、COM 経由ならフォーカスと無関係に進められる

### プラグインは不要

アドイン登録・VBA・マクロのセキュリティ設定変更はいずれも不要（COM 自動化はマクロ実行ではない）。既存の `win32com.client.Dispatch("PowerPoint.Application")`（[pptmerge/_merger.py:688](../src/md_merge/pptmerge/_merger.py), [pptpdfexport/__init__.py:129](../src/md_merge/pptpdfexport/__init__.py)）と同じ入口で、`pywin32` は既に依存に入っている。必要なのはデスクトップ版 PowerPoint と同一ユーザーセッションのみ（管理者権限・DCOM 設定は不要）。

### キャプチャ方法

- スライドショーを**全画面ではなくウィンドウ表示**で起動し、**Windows Graphics Capture**（Win10 1803+、HWND 単位）でそのウィンドウだけを取る。他ウィンドウに隠れていても GPU 描画でも取得できるため、裏で進行させながら別作業ができる
- `PrintWindow`（`PW_RENDERFULLCONTENT`）はスライドショーが Direct3D 描画のため黒画像になりやすい。素の BitBlt は前面必須

### 制約

- **最小化は不可**（描画が止まる）、**セッションロック中も不可**（合成が止まる）→ **無人のスケジュール実行はできない**
- PowerPoint は Excel / Word と違い不可視モードが実質使えない（既存コードも `Visible = True`）。ウィンドウが画面に出ることは避けられず、避けられるのは「全画面を占有すること」まで
- 解像度は画面ピクセル依存。16:9 ワイド（13.333 インチ幅）で 1920px ≒ 144 DPI 相当＝現行既定 `_DEFAULT_DPI = 150` とほぼ同等、4K なら 288 DPI 相当。品質は足りるが、**使うモニタで結果が変わる＝再現性がない**のが弱点
- **同期が最大の難所**: `Next()` は即座に戻り、アニメーションはその後再生される。完了イベントがないため、固定 sleep では再生途中を撮る。実用的には「連続キャプチャして前フレームと同一になったら確定」の差分収束待ちが必要
- 落とし穴: 発表者ビューが開くと画面構成が変わる（明示的に無効化）、マルチモニタでどの画面に出るか、更新通知等のダイアログ割り込み、数式オブジェクト入り pptx が COM を壊す既知の問題、新規プロファイルでの初回起動ダイアログ

### 既存コードとの接続は素直

クロップは [`_to_ltrb_float`](../src/md_merge/pptimgexport/__init__.py) でシェイプ座標をスライド寸法に対するパーセントへ正規化しており**解像度非依存**。したがって「PDF ページをラスタライズする」部分を「キャプチャしたフレーム」に差し替えれば、`named_shape` / `slide_with_rectpct` の切り出しロジックはそのまま再利用できる。交換するのは画像ソースだけ。

## 5. 試作の結果（2026-10-09）

試作スクリプト: **[tools/pptx_step_capture.py](../tools/pptx_step_capture.py)**（単独で動く。`md_merge` 本体には未接続）

対象: 作者の環境にある実験用の `steps-exp.pptx`（スライド 3 に 7 ステップ、すべて単純な開始アニメーション）

### 5.1 確認できたこと

| 確認項目 | 結果 |
|---|---|
| ステップ数の取得 | **OK**。ウィンドウ表示のスライドショーで `GetClickCount()` = **7**。オフラインで数えた `p:timing` の `clickEffect` 数（7）と一致 |
| ステップごとのキャプチャ | **OK**。step 0（クリック前）＋ 7 ステップの計 8 枚を取得。真っ黒ゼロ。隣接ステップ間の差分も毎回別領域に出ており、段階が正しく進んでいる |
| キャプチャ方法 | `PrintWindow(PW_RENDERFULLCONTENT)` がウィンドウ表示のスライドショーで**機能した**（黒画像にならない）。前面に出す必要も画面全体を占有する必要もなかった |
| 同期（差分収束待ち） | **OK**。1 ステップあたり 2〜3 フレーム、0.25〜0.44 秒で収束。固定 sleep なしで足りる |
| ステップ移動 | `View.GotoClick(k)` で決定的に移動できた（`Next()` の連打も `--use-next` で選択可） |
| 解像度 | スライド領域 **1966x1106px = 約 147 DPI 相当**。`pptimgexport` の既定 150 DPI とほぼ同等 |
| 既存クロップの流用 | **OK**。`--crop-shape exportrange` で `_to_ltrb_float` の % 正規化をそのまま適用し 1530x895 を切り出せた。画像ソースを差し替えるだけで既存のクロップが使えるという §4 の見立ては正しかった |

### 5.2 実装で判明した落とし穴（設計時には見えていなかったもの）

- **`SlideShowWindow.HWND` は使えない。** 遅延バインディングではプロパティでなくメソッドとして見え、呼んでも HWND を返さない。代わりに、スライドショー起動の**前後で増えた `PPTFrameClass` ウィンドウ**を差分で特定する方式にした（タイトル文字列はローカライズされるため当てにしない）。ウィンドウ表示のスライドショーは PowerPoint 本体と**同じクラス名**の別ウィンドウとして出る
- **ブラウズ（ウィンドウ）表示には右端に縦スクロールバーが付く。** そのためクライアント領域の中心＝スライドの中心にならず、「クライアント領域をスライド比で中央切り出し」ではズレる。黒帯（レターボックス）を実測で落としてから縦横比にスナップし、余剰幅を右から削る方式で解決した
- 1 回の実行で PowerPoint の起動〜8 枚取得まで十数秒。キャプチャ中にウィンドウは画面に出るが、前面である必要はない

### 5.3 残る課題

- Windows Graphics Capture は**使わずに済んだ**（PrintWindow で足りた）。最小化・セッションロック中が不可である点は変わらないので、無人実行はできない
- 解像度がウィンドウサイズ依存である点は未解決（§6-3）
- 段落単位のビルドや終了アニメーションを含むスライドでの挙動は未検証（今回の対象は開始アニメーションのみ）

## 6. 採用方針（2026-10-23 決定）

### 6.1 決定事項

| 項目 | 決定 |
|---|---|
| 方式 | **案 C**（COM でスライドショーを駆動し、ウィンドウをキャプチャ）。案 B は採らない |
| 置き場所 | 新サブコマンドは作らず **`pptimgexport` の画像ソース切り替え**として組み込む。ステップ指定のあるタスクだけがキャプチャ経路に回り、それ以外は従来どおり PDF から切り出す |
| ノート記法 | 既存の `{{BLOCK:IMAGE}}` に **`export-image-step:` キーを 1 つ足す**（§6.2）。新しいブロック型は作らない |
| 解像度 | **レシピの `dpi`（既定 150）に固定**。キャプチャ画像をスライド全体の段階で `スライド寸法（インチ）× dpi` px へ正確にリサンプルしてから切り出す（§6.3） |

### 6.2 ノート記法

`export-image-mode` / `export-image-target` / `export-image-inset` はそのまま使え、意味も変わらない。

```
{{BLOCK:IMAGE}}

export-image-mode: slide_with_rectpct
export-image-target: exportrange
export-image-step: 2
export-image: ../images/<__BASEFILENAME__>_slide<__SLIDENUM__>_step2.png
```

複数ステップは 1 ブロックにまとめて書ける。その場合 `export-image:` に `<__STEP__>` が必須。

```
{{BLOCK:IMAGE}}

export-image-mode: slide_with_rectpct
export-image-target: exportrange
export-image-step: 0-3, 5
export-image: ../images/<__BASEFILENAME__>_slide<__SLIDENUM__>_step<__STEP__>.png
```

| `export-image-step` の値 | 意味 |
|---|---|
| 省略（空） | **従来どおり PDF から切り出す**（最終状態）。既存ノートは影響を受けない |
| `0` | クリック前の状態（`GotoSlide` 直後） |
| `N` | N 回クリックした後の状態（`GotoClick(N)`） |
| `0-3, 5` | 範囲とカンマ区切りの組み合わせ。重複は 1 つにまとめ、昇順に処理 |
| `all` | `0` 〜 `GetClickCount()` の全ステップ |
| `last` | `GetClickCount()` と同じ。最終状態をキャプチャ経路で撮る（PDF 画像と見た目を揃えたいとき用） |

- `<__STEP__>` は `export-image:` の中でだけ、**タスクごと（ステップ単位）に**展開する。ノート全体のプレースホルダー置換（`<__SLIDENUM__>` 等）の後で行う。桁は素の整数（`step2`）
- 複数ステップ（範囲・カンマ・`all`）なのに `<__STEP__>` が無い → 全ステップが同じファイルに上書きされるので**そのブロックはエラー**
- 指定ステップが `GetClickCount()` を超える → そのタスクを失敗にする（終了コード 1）
- アニメーションが 0 個のスライドに `export-image-step` → step 0 だけが有効（`all` / `last` は 0 になる）
- Windows 以外でステップ指定がある → そのタスクを失敗にする。PDF 経路のタスクは通常どおり実行
- `--dry-run` では PowerPoint を起動しない。ステップ数が分からないので `all` / `last` は展開せずに表示する
- MD 側の参照は従来と同じ（`![手順1](../images/…_step1.png)`）

### 6.3 解像度を `dpi` に揃える

ウィンドウサイズだけで揃えるのはモニタ依存で不確実なので、2 段構えにする。

1. **ウィンドウを目標以上に広げる。** `SlideShowWindow.Width/Height`（pt）を、スライド領域が `スライド幅（インチ）× dpi` px 以上になる大きさに設定する（16:9・150 DPI なら 2000×1125px）。画面より大きくできない環境では取れる大きさで撮る（ただし小さい画面での運用は想定しない。§6.5）
2. **スライド領域を目標寸法へリサンプル（Lanczos）してから切り出す。** 出力のピクセル寸法は PDF 経路と**完全に一致**し、モニタに依存しない。キャプチャが目標より小さく**拡大率が 1.05 を超えたら警告**（画質が落ちるため）

`dpi` はレシピの `input.cropsrc[].dpi` をそのまま使い、PDF 経路と設定を共有する。

### 6.4 実装の構成

- `pptimgexport/_capture.py`: 試作（`tools/pptx_step_capture.py`）から COM 起動・スライドショー HWND の特定・`PrintWindow` キャプチャ・差分収束待ち・黒帯除去を移植。pptx 1 つにつきスライドショーを 1 回起動し、そのファイルのステップ指定タスクをまとめて撮る
- `pptimgexport/__init__.py`: `export-image-step` の解析とタスク展開、PDF 経路とキャプチャ経路の振り分け。クロップは同じ `_to_ltrb_float` の % 座標と `export-image-inset` を共用
- 数式オブジェクト入り pptx が COM を壊す既知の問題は、キャプチャ経路にもそのまま当てはまる（`--preprocess` 済み pptx を開く）

### 6.5 実装の確認結果（2026-10-23）

対象は §5 と同じ pptx（スライド 3 に 7 ステップ）。ノートに `all` / `0, 7` / ステップ指定なし（PDF）の 3 ブロックを並べて実行した。

| 確認項目 | 結果 |
|---|---|
| 出力寸法 | **OK**。キャプチャ経路の全体画像が 2000×1125px、`exportrange` 切り出しが 1556×911px。いずれも PDF 経路（150 DPI）と**完全に一致** |
| ウィンドウの自動拡大 | **OK**。初期のスライド領域 1890×1063px → 拡大後 2043×1149px（目標 2000 以上）→ 縮小リサンプル。拡大警告は出ない |
| PDF との見た目の差 | 最終ステップのキャプチャと PDF 画像の平均差は 255 段階中 約 2.9。差が 40 を超える画素は 2.5%（文字のアンチエイリアス）。目視では区別できない |
| 非表示スライド | **OK**。スライドショーでも `GotoSlide` で表示・キャプチャできた（失敗扱いにする必要はなかった） |
| 異常系 | 書式不正・`<__STEP__>` 無しの複数指定・ステップ数超過は、それぞれ該当分だけ失敗し終了コード 1。アニメーションなしのスライドの `last` は step 0 として撮れる |

未確認のまま残っている点:

1. **段落単位のビルド・終了アニメーション**: `GotoClick` は描画結果をそのまま撮るので原理的には対応するはずだが未検証

**対象外とした点（2026-10-23 決定）:** 目標寸法より小さい画面での運用は**想定しない**。画面が足りない環境で `PrintWindow` が画面外の部分まで撮れるかは検証していない（その場合の挙動は §6.3 の「拡大＋警告」止まり）。小さい画面で動かす必要が出てきたら、その段階で検討する。

## 7. 未決事項

1. **再現性の残り**: §6.3 でピクセル寸法は揃うが、描画そのもの（ClearType、GPU）は環境で僅かに変わる。仮想ディスプレイ等で環境を固定するかは、実運用で差が問題になってから判断する
2. **無人実行**: 案 C は対話セッション必須（最小化・ロック中は不可）。スケジュール実行が必要になったら案 B を再検討する
